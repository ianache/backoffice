**service.py — two new functions:**

Add `add_segment_to_flag()` — inserts into flag_segments join table. Returns the Segment object if success, None if flag/segment not found. Uses `select(FlagSegment)` to check for existing link first to avoid duplicate PK error.

```python
from .models import FeatureFlag, Segment, FlagSegment

async def add_segment_to_flag(
    db: AsyncSession,
    flag_id: int,
    segment_id: int,
) -> Optional[Segment]:
    # Verify flag and segment exist
    flag = await get_flag(db, flag_id)
    segment = await get_segment(db, segment_id)
    if not flag or not segment:
        return None
    # Check for existing link (avoid PK conflict)
    existing = await db.execute(
        select(FlagSegment).where(
            FlagSegment.flag_id == flag_id,
            FlagSegment.segment_id == segment_id,
        )
    )
    if existing.scalar_one_or_none():
        return segment  # Already linked — idempotent
    link = FlagSegment(flag_id=flag_id, segment_id=segment_id)
    db.add(link)
    await db.commit()
    return segment


async def get_flag_segments(
    db: AsyncSession,
    flag_id: int,
) -> list[Segment]:
    stmt = (
        select(Segment)
        .join(FlagSegment, FlagSegment.segment_id == Segment.id)
        .where(FlagSegment.flag_id == flag_id)
    )
    result = await db.execute(stmt)
    return list(result.scalars().all())
```

Also import `FlagSegment` in service.py (currently only imports `FeatureFlag, Segment`).

Modify `evaluate_flag()` in service.py to accept and use `segment_members` from context.

The `context` dict currently has keys: `tenant_id`, `product_id`, `company_id`, `user`. Add optional key `segment_members` which is a dict mapping `flag_id → list[str]` (list of user UUIDs in all segments linked to that flag). The caller (router endpoint) will pre-fetch this data before calling evaluate_flag().

**Why dict by flag_id instead of a simple list:** evaluate_flag() receives multiple flag rows (all rows for a given flag name). Different rows (different scopes) may have different segment associations. Pre-keying by flag_id allows O(1) lookup per candidate.

**Modified evaluate_flag() logic — insert AFTER the inline rules loop, BEFORE the default return:**

```python
def evaluate_flag(flags: list, context: dict) -> bool:
    # ... existing candidates selection and winner determination (unchanged) ...
    
    if not winner.enabled:
        return False

    # Evaluate inline rules — first matching rule wins
    rules_raw = winner.rules
    rules = json.loads(rules_raw) if isinstance(rules_raw, str) and rules_raw else (rules_raw if isinstance(rules_raw, list) else [])
    user = context.get('user', {})
    for rule in rules:
        if _evaluate_rule(rule, user):
            return bool(rule.get('result', winner.default_val))

    # If no inline rule matched, check segment membership
    # context['segment_members'] is a dict: {flag_id: [user_uuid, ...]}
    segment_members = context.get('segment_members', {})
    user_id = user.get('id') or user.get('sub')  # Try both common key names
    if user_id and winner.id in segment_members:
        if user_id in segment_members[winner.id]:
            return True  # User is in a linked segment — flag evaluates as enabled

    return bool(winner.default_val)
```

**Important:** The evaluation uses `any-match` semantics for segments: if the user is in ANY linked segment, the flag evaluates to True. This matches FLAG-06 intent (segments are targeting mechanisms).
