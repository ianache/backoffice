# Phase 17 — UI Design Contract: Observability Dashboard (mui-observability)

## Spacing Scale

Reuses the existing project scale — already mapped in `tailwind.config.js` `theme.extend.spacing` (`xs`/`sm`/`md`/`lg`/`xl` → CSS vars `--spacing-xs..xl`):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon gaps, badge dot spacing, inline padding |
| sm | 8px | Compact element spacing, chip padding |
| md | 16px | Default element spacing, card padding |
| lg | 24px | Section padding, gap between status cards |
| xl | 32px | Layout gaps between major dashboard sections |
| 2xl | 48px | Major section breaks (not yet in tailwind.config — use `gap-12` raw if needed) |
| 3xl | 64px | Page-level spacing (not yet in tailwind.config — use `gap-16` raw if needed) |

Exceptions:
- Status card grid uses `gap-md` (16px) between the 5 cards — matches `TenantTable.vue`/`LabelingView.vue` grid gap conventions.
- Range selector buttons (24h/7d/30d) use `gap-xs` (4px) between segments, `px-md py-1` (4px) per segment — mirrors the toggle-button pattern in `LabelingView.vue` header buttons. This matches the "Range Selector anatomy" section exactly.
- Chart canvas containers reserve `min-h-[280px]` per chart (chart.js requires explicit container height) — not a spacing-scale token but a layout constraint, document inline as a Tailwind arbitrary value.

## Typography

Reuses `microuis/mui-labeling/tailwind.config.js` `fontSize` scale exactly (already declared, do not add new sizes):

| Role | Size | Weight | Line Height | Tailwind class |
|------|------|--------|-------------|----------------|
| Body | 16px | 400 (regular) | 24px (1.5) | `text-body-md` |
| Label | 12px | 700 (bold) | 16px (1.33) | `text-label-sm` (used for status badges, uppercase tags) |
| Heading | 24px | 700 (bold) | 32px (1.33) | `text-headline-md font-bold` (page title "Observability") |
| Display | 32px | 400 + tabular-nums | 40px (1.25) | `text-headline-lg` — reserved for the single biggest number on a status card (e.g., uptime % or current latency value), per existing `AuditLogView.vue` `text-headline-lg` page-title precedent repurposed here as the "hero metric" |

**Declared weights (exactly 2):** 400 (regular, body text/values) and 700 (bold, labels/badges/headings). `text-headline-md` and `text-headline-lg` use `font-bold` (700) wherever they appear in this spec — `font-semibold` (600) is NOT used anywhere in this document. No 3rd weight and no 500 are introduced.

**Numeric values (latency ms, uptime %, p95/p99):** apply `font-mono tabular-nums` (matches `TenantTable.vue` `created_at` column convention) so digits align in status cards and tables.

## Layout Contract

No mockup exists, so this section is prescriptive and authoritative for the executor.

### Page structure (`ObservabilityView.vue`)

```
┌─────────────────────────────────────────────────────────────────┐
│ Page Header                                                        │
│   h1 "Observability" (text-headline-lg font-bold)                  │
│   p  "Real-time health, latency trends..." (text-body-md, on-      │
│       surface-variant)                                              │
├─────────────────────────────────────────────────────────────────┤
│ Range Selector (top-right aligned, or below header on mobile)      │
│   [ 24h ] [ 7d ] [ 30d ]   <- segmented control, active = primary  │
├─────────────────────────────────────────────────────────────────┤
│ Service Status (Section heading, text-title-lg font-bold)          │
│   ┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐         │
│   │ Status │ │ Status │ │ Status │ │ Status │ │ Status │         │
│   │ Card 1 │ │ Card 2 │ │ Card 3 │ │ Card 4 │ │ Card 5 │         │
│   └────────┘ └────────┘ └────────┘ └────────┘ └────────┘         │
│   grid-cols-1 sm:grid-cols-2 lg:grid-cols-5, gap-md                │
├─────────────────────────────────────────────────────────────────┤
│ Latency Trend (Section heading)                                     │
│   ┌─────────────────────────────────────────────────────────┐    │
│   │  <Line> chart.js — 5 datasets (one per service)           │    │
│   │  X axis: time buckets (per range)                          │    │
│   │  Y axis: latency_ms                                         │    │
│   │  Legend: top, service color chips                           │    │
│   │  min-h-[280px]                                               │    │
│   └─────────────────────────────────────────────────────────┘    │
├─────────────────────────────────────────────────────────────────┤
│ Uptime (SLO) (Section heading)                                      │
│   grid-cols-1 sm:grid-cols-2 lg:grid-cols-5, gap-md                │
│   ┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐         │
│   │ Uptime │ │ Uptime │ │ Uptime │ │ Uptime │ │ Uptime │         │
│   │ Summary│ │ Summary│ │ Summary│ │ Summary│ │ Summary│         │
│   └────────┘ └────────┘ └────────┘ └────────┘ └────────┘         │
└─────────────────────────────────────────────────────────────────┘
```

**Latency Trend data source (RESOLVED data contract — D-13/OBS-08):** the X-axis "time buckets (per range)" are NOT derived client-side from scalar aggregates. They come from the backend metrics `history` series: `GET /observability/metrics?range=X` returns, per service, `history: [{ ts, avg_latency_ms }, ...]` (hourly buckets for 24h, daily buckets for 7d/30d — see 17-01/17-02 plans). `ObservabilityView` maps this into `LatencyTrendChart`'s contract: `labels` = the ordered bucket `ts` values, and one `dataset` per service whose `data[]` is that service's `avg_latency_ms` per bucket (null where a bucket is missing so the line gaps). The chart is a genuine time-series latency trend, not a single-point-per-range comparison.

### Status card anatomy (`StatusCard.vue`)

```
┌──────────────────────────────┐
│ FastAPI Core         [● UP]   │  <- name (text-title-md font-bold) + status-chip badge (right-aligned)
│                                │
│   42 ms                        │  <- hero metric (text-headline-lg font-mono tabular-nums)
│   current latency               │  <- caption (text-label-sm text-on-surface-variant uppercase)
└──────────────────────────────┘
```
- Card shell: `bg-surface-container-lowest border border-outline-variant rounded-xl p-md shadow-sm`
- DOWN state: card border becomes `border-error/40` and hero metric shows "—" with caption "unreachable"
- DEGRADED state: hero metric color becomes amber-on-container text (matches `.status-pending` text color) to reinforce the badge without relying on the badge alone (color + text redundancy for accessibility)

### Uptime summary card anatomy (`UptimeSummary.vue`)

```
┌──────────────────────────────┐
│ FastAPI Core                    │  <- name (text-title-md font-bold)
│   99.8%                          │  <- hero metric (text-headline-lg font-mono tabular-nums), green if >=99.9%, amber if 99.0-99.89%, red if <99.0%
│   uptime                          │  <- caption (text-label-sm uppercase)
│   ─────────────────────────────  │
│   p95: 38ms   p99: 95ms          │  <- secondary stats row (text-body-md font-mono)
│   error rate: 0.2%                │
└──────────────────────────────┘
```
- Uptime hero-metric color thresholds reuse the SAME 3-tier semantic colors as status badges (green/amber/red) — directly visualizes SLA health without a separate legend.
- SLO breach indicator: if `p95_latency_ms > 100`, render a small `error`-colored icon (`material-symbols-outlined` "warning", `text-error text-[16px]`) next to "p95: Nms" with tooltip "SLO breach".

### Range selector anatomy (`RangeSelector.vue`)

```
[ 24h ] [ 7d ] [ 30d ]
```
- Container: `inline-flex items-center gap-xs p-xs bg-surface-container rounded-full` (pill-shaped segmented control)
- Active segment: `bg-primary text-on-primary font-bold rounded-full px-md py-1`
- Inactive segment: `text-on-surface-variant hover:bg-surface-container-high rounded-full px-md py-1`
- Default selection: `24h` on mount

### Loading / Empty / Error states

- **Loading:** Centered text `"Loading service health…"` in `text-on-surface-variant py-xl` — matches `AuditLogView.vue` loading-state pattern exactly (line 234-236).
- **Empty** (no samples yet — e.g., health checker just started): Card shell `bg-surface-container-lowest border border-outline-variant rounded-xl text-center py-xl` containing heading "No health data yet" (`text-title-md font-bold`) + body copy (`text-body-md text-on-surface-variant mt-1`). The Latency Trend section shows this same Empty state when every service's `history` array is empty (no chart rendered until buckets exist).
- **Error** (BFF/backend unreachable): Same card shell, `border-error/40`, heading uses `material-symbols-outlined text-error` "error" icon + "Unable to load observability data." body copy. Per PRD §10.2, this state must NOT block the rest of the portal — it is scoped to this view only.

### Auto-refresh

- Status cards poll `GET /observability/health/services` every 15s (matches health-checker interval) via `setInterval`, cleared on `onUnmounted` — mirrors WS-free polling already used elsewhere (no new WS channel needed for Phase 17; Phase 19 may add push updates).
- Latency trend + uptime summary re-fetch `GET /observability/metrics?range=X` only when the range selector changes (not on the 15s poll — historical aggregates don't need second-level freshness). The `history` series re-buckets per range (hourly for 24h, daily for 7d/30d).
